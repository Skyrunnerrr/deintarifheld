# ADR-013 — External Action / Outbox Pattern

STATUS=ACCEPTED
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
External Action / Outbox Pattern must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
External actions (mail/calendar/social) go Workflow→Command→Policy→Adapter→Outbox→Provider→Readback→Communication event. Idempotency keys mandatory.

## Why
Handles provider timeout ambiguity; enables reconciliation.

## Rejected options
Direct fire-and-forget from request path; blind retries.

## Security impact
Prevents duplicate customer mail.

## Privacy impact
Communication records support purpose/suppression later.

## Operations impact
Requires worker reliability.

## Migration impact
Customer mail remains disabled until gates.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.

## Open questions
Listed in DTH-M9.md where verification still required.

## Evidence references
docs/autonomous-os/evidence-reports/DTH-M8.md, DTH-M8C.md, DTH-M9.md; repo inventory (root app/api, packages/*).
