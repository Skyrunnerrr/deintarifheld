# ADR-016 — Migration Ownership Boundary

STATUS=ACCEPTED_WITH_M10_DEPENDENCY
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Migration Ownership Boundary must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
M9: one logical migration authority process; public intake SQL and Ops SQL may share repo tooling but must have clear OWNERS and apply gates. packages/db drafts are design source; supabase/migrations is apply root. M10 decides schemas/SoT/lead→case semantics and whether separate DB projects/schemas are required.

## Why
Prevents ambiguous dual-draft ownership (M8C).

## Rejected options
Silent dual apply roots without owners; choosing final table layouts in M9.

## Security impact
Reduces accidental prod migration.

## Privacy impact
Supports future schema separation if M10 requires.

## Operations impact
Process discipline needed.

## Migration impact
No migration execution in M9.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.
