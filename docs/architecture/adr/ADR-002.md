# ADR-002 — Canonical Ops Runtime

STATUS=ACCEPTED
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Canonical Ops Runtime must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
Canonical Ops runtime is packages/ops-api + packages/cc + packages/workers + packages/shared + packages/db. packages/web and packages/api remain non-canonical skeletons to deprecate.

## Why
Real local Ops code already lives there; skeletons are empty boundaries that would create false consolidation.

## Rejected options
Absorbing Ops into root Next (Option C) as primary long-term shape; inventing new services.

## Security impact
Ops AuthZ/session/kill can evolve without redeploying public site.

## Privacy impact
Ops data access confined behind Ops API.

## Operations impact
Separate deployables increase clarity of incidents.

## Migration impact
Continue local Ops; no production Ops deploy until AuthZ/RLS/mapping gates.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.
