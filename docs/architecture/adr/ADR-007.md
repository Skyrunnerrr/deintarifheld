# ADR-007 — Durable Session State

STATUS=ACCEPTED
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Durable Session State must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
Production session coordination uses Postgres-backed registry (provider-centric Clerk session + DTH durable registry for max-one / revoke-old / disablement). Redis not required initially.

## Why
Reuses existing DB; multi-instance safe; fewer new failure domains (P19).

## Rejected options
Redis-first; pure Clerk-only without DTH registry; remaining in-memory.

## Security impact
Enables horizontal session policy.

## Privacy impact
Session metadata minimization required (M10).

## Operations impact
DB becomes dependency for Ops session enforcement — acceptable for Ops plane.

## Migration impact
Local in-memory may remain for LOCAL only.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.

## Open questions
Listed in DTH-M9.md where verification still required.
