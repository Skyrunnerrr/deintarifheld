# ADR-005 — Database Access Boundary

STATUS=ACCEPTED
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Database Access Boundary must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
Browsers and Agents never talk to DB. CC and Agents call Ops API. Workers use constrained DB credentials for claimed jobs. Public API uses constrained intake credential only.

## Why
Enforces AuthZ/policy chokepoint; contains service-role risk (M8C).

## Rejected options
CC→Supabase direct; Agent→DB; Public API retaining unrestricted service_role as target end-state.

## Security impact
Attack surface shrinks to API/worker principals.

## Privacy impact
Supports purpose limitation per runtime.

## Operations impact
Requires Ops API maturity before CC features expand.

## Migration impact
No schema change in M9.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.
