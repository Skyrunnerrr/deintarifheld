# ADR-006 — Credential / Service Principal Boundary

STATUS=ACCEPTED_WITH_M10_DEPENDENCY
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Credential / Service Principal Boundary must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
Every runtime gets an explicit credential with scoped purpose. Unrestricted service_role is not the target for public intake. Target: narrow INSERT/limited write for intake; separate Ops reader/writer; worker claimer; no agent-held DB secrets; no Clerk admin secret in agents.

## Why
SERVICE_ROLE_BYPASS_RISK=YES today; architecture must make bypass explicit and minimized.

## Rejected options
Shared superuser credential across public+ops+worker+agent.

## Security impact
Blast-radius reduction.

## Privacy impact
Least privilege / data minimization.

## Operations impact
More secrets to rotate — acceptable.

## Migration impact
Current prod credentials unchanged until implementation tranche; M9 only defines target matrix.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.
