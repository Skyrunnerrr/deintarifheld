# ADR-033 — Runtime DB Role Assumption & Physical Schema Isolation

STATUS=ACCEPTED
TRANCHE=DTH-M10R  
DATE=2026-08-13  

## Context
M10 defined conceptual principals (PUBLIC_INTAKE, OPS_API, WORKER, …) but did not specify how Vercel/Ops runtimes actually assume those Postgres identities. Current production public path uses Supabase Data API with `service_role`, which has `BYPASSRLS`. Logical domains alone leave Ops/Security/Workflow/Audit casually exposable via Data API if they remain in exposed schemas.

## Binding platform facts
- PostgREST switches role from JWT `role` claim; `service_role` bypasses RLS.
- Supabase Data API exposes configured schemas; `public` is exposed by default; private schemas should hold non-API tables.
- Table owners and BYPASSRLS roles bypass RLS unless FORCE ROW LEVEL SECURITY applies.

## Decision

### 1) Canonical role-assumption pattern
```text
CANONICAL_ROLE_ASSUMPTION_PATTERN=DIRECT_POSTGRES_LOGIN_ROLE
```
Trusted server runtimes (Root Public Intake API, Ops API, Workers) connect with dedicated Postgres LOGIN roles via direct connection / pooler — **not** via `service_role` Data API as the target path.

| RUNTIME | POSTGRES_ROLE | PATH | DATA_API | BYPASSRLS |
|---|---|---|---|---|
| Root Public Intake | `dth_public_intake` | Direct PG / pooler | NO (target) | NO |
| Ops API | `dth_ops_api` | Direct PG / pooler | NO | NO |
| Worker | `dth_worker` | Direct PG / pooler | NO | NO |
| Migration | `dth_migration` (or controlled postgres) | Offline migrate only | NO | MAYBE offline exception |
| CC / Agent | none | Ops API / tools only | NO | N/A |

Rejected as **target** PUBLIC_INTAKE mechanism: Data API + `service_role` (BYPASSRLS / project-wide privilege).

Optional future: JWT custom role through Data API for narrow intake — only if equivalent least privilege proven; **not** required and not preferred for atomic intake.

### 2) Physical schema isolation
```text
PHYSICAL_SCHEMA_ISOLATION=REQUIRED
```
| Domain | TARGET_PHYSICAL_SCHEMA | EXPOSED_TO_DATA_API |
|---|---|---|
| PUBLIC_INTAKE surface | `intake` (or intentionally limited `api`/`public` during transition) | YES only if deliberately required; prefer server direct PG |
| OPS | `ops` | NO |
| SECURITY | `security` | NO |
| WORKFLOW | `workflow` | NO |
| AUDIT | `audit` | NO |

Sensitive domains must not rely on RLS alone while remaining Data-API-exposed.

### 3) Table ownership
```text
RUNTIME_ROLE_MUST_NOT_OWN_PROTECTED_TABLE
TABLE_OWNER_ROLE=dth_migration / DDL owner (not runtime)
```
Runtime roles are grantees only. Prefer `FORCE ROW LEVEL SECURITY` on protected tables as defense-in-depth.

### 4) Atomic public intake
```text
PUBLIC_INTAKE_ATOMIC_TRANSACTION_PATTERN=SERVER_DIRECT_POSTGRES_TRANSACTION
```
Lead/career + source outbox + minimal intake audit in **one** Postgres transaction in the public API process. Two sequential Data API calls are **not** atomic and are rejected as the target pattern.

SECURITY DEFINER intake RPC is exceptional; prefer INVOKER / direct txn with LOGIN role privileges.

## Rejected options
- Conceptual role without assumption mechanism
- service_role as permanent PUBLIC_INTAKE
- Leaving Ops/Security/Workflow/Audit physical schema optional forever
- Runtime roles as table owners
- Dual HTTP inserts as “same transaction”

## Security / privacy / ops impact
Closes paper least-privilege gap; shrinks Data API blast radius; enables real atomic handoff; slightly more connection management than pure Data API — acceptable for small team and already aligned with Ops `pg` Pool pattern.

## Open questions (M11)
Exact role names, pooler config, schema rename/migrate sequence, FORCE RLS rollout order.

## M10F FREEZE
STATUS=ACCEPTED. Binding for implementation. No SQL in this tranche.
