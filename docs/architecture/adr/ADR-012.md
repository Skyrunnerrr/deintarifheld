# ADR-012 — Agent Tool Boundary

STATUS=ACCEPTED
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Agent Tool Boundary must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
Agents are untrusted principals: structured tools → domain API → policy → AuthZ → action → audit. No service_role, no Clerk admin, no raw provider keys, no human session impersonation.

## Why
OWASP agency / injection risks; Master Plan AI layer high in stack.

## Rejected options
Agent with DB URL; agent with Resend key; free orchestration.

## Security impact
Capability minimization.

## Privacy impact
Data minimization per tool.

## Operations impact
Slower agent iteration — required.

## Migration impact
Future only; no agent impl in M9.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.
