# ADR-010 — Command Center Boundary

STATUS=ACCEPTED
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Command Center Boundary must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
CC remains a separate UI deployable (packages/cc), authenticated via IdP, authorized via Ops API only — no direct DB.

## Why
Separates browser attack surface; matches existing package; avoids coupling public Next to Ops UI.

## Rejected options
CC as route group inside public Next permanently.

## Security impact
XSS in CC cannot directly hold DB service role.

## Privacy impact
Operator UI should not widen public cookie domain.

## Operations impact
Extra deploy; shared packages via workspace.

## Migration impact
Local CC continues; prod CC after AuthZ/mapping/RLS.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.
