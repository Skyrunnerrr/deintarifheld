# ADR-004 — Public-to-Ops Handoff

STATUS=ACCEPTED_WITH_M10_DEPENDENCY
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Public-to-Ops Handoff must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
Canonical pattern: durable public intake write first, then asynchronous handoff into Ops (transactional outbox / intake event + worker). Not synchronous CC dependency; not polling Sheets.

## Why
Preserves lead capture if Ops down; enables idempotent retries; aligns with existing outbox draft intent.

## Rejected options
Same-transaction direct Ops case create from public API; sync API-to-API as sole path; Google import.

## Security impact
Limits public credential need to intake write; reduces coupling.

## Privacy impact
Minimizes purpose mixing at write time.

## Operations impact
Ops lag possible — requires monitoring/reconciliation.

## Migration impact
M10 defines exact event/case records; public insert path stays.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.
