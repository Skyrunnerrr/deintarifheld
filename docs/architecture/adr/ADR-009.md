# ADR-009 — Workflow Runtime

STATUS=ACCEPTED
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Workflow Runtime must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
Initial workflow runtime = Postgres (events/commands/jobs/outbox) + worker + scheduled runner. Specialized queues (SQS/Redis) deferred until proven need.

## Why
Sufficient for lead loop V1; lowest ops cost; aligns with draft outbox tables.

## Rejected options
Immediate microservice workflow engine; Kafka.

## Security impact
Central policy before actions.

## Privacy impact
Job payloads must be minimized.

## Operations impact
Single DB is both SoT and queue — monitor contention.

## Migration impact
Implement only after M10 + AuthZ foundations.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.

## Open questions
Listed in DTH-M9.md where verification still required.

docs/autonomous-os/evidence-reports/DTH-M8.md, DTH-M8C.md, DTH-M9.md; repo inventory (root app/api, packages/*).
