# ADR-003 — Deployment Boundary

STATUS=ACCEPTED
TRANCHE=DTH-M9  
DATE=2026-08-13  

## Context
Phase-4 dual-plane reality (root public LIVE; packages Ops LOCAL) frozen at M8C `4545c7b`. Architecture must support secure Ops, durable workflows, and future agents without big-bang rewrite of working public intake.

## Problem
Deployment Boundary must be decided before implementation so later AuthZ/RLS/workflow work does not accidentally entrench the wrong topology.

## Constraints
- No microservices without need (P20)
- Public intake must not depend on CC/AI (availability)
- RLS ≠ protection from service-role (M8C)
- In-memory controls not production-suitable
- Implementation not authorized in M9

## Options considered
See DTH-M9 evidence report scorecard (Options A/B/C).

## Decision
At least two production deployables long-term: (1) Public Web/API plane; (2) Ops API (+ CC UI and Worker as separate or co-located Ops deployables). Public and Ops must not share process credentials.

## Why
Failure isolation: CC/worker outage must not take down lead intake.

## Rejected options
Single monolithic deploy for public+ops permanently.

## Security impact
Credential and compromise blast radius reduced.

## Privacy impact
Environment separation easier.

## Operations impact
More deploy pipelines but clearer rollback units.

## Migration impact
Transition: keep public as today; introduce Ops deploy only after staging gates.

## Rollback
Architecture decision can be revised before implementation starts; after impl, follow ADR-specific rollback in implementation tranche.

## Dependencies
M8C baseline; M10 for data/SOT details; M6 does not block this ADR.
